# B0 — The `count` trap

What does `terraform plan` show when a middle landlord account is removed from the list? Why is
that dangerous here? What's the fix?

# B0 — Terraform count and resource identity

## Problem

The landlord media S3 buckets use `count = length(var.landlord_accounts)`.
Each bucket is identified by its numeric index, such as
`aws_s3_bucket.landlord_media[1]`, rather than by a stable landlord ID.

## Reproduced result

The original list was:

`["la-001", "la-002", "la-003", "la-004"]`

After removing `la-002`, the list becomes:

`["la-001", "la-003", "la-004"]`

I ran:

`terraform -chdir=terraform plan -refresh=false`

The plan proposed:
- Replacing index [1]: bucket name changes from
  `haven-media-la-002` to `haven-media-la-003`.
- Replacing index [2]: bucket name changes from
  `haven-media-la-003` to `haven-media-la-004`.
- Destroying index [3], because it is outside the new count range.

The full plan reported 4 additions and 3 destructions.
Two additions and two destructions are associated with the
bucket replacements; the other two additions are the separate
listing media bucket and lifecycle configuration.

## Risk

A positional index is not a stable identity. Removing an item
from the middle shifts subsequent list positions, so Terraform
can associate existing infrastructure with the wrong landlord.
S3 bucket name changes require replacement, potentially causing
data availability, data loss, and service disruption risks.

## Fix

Use `for_each` keyed by stable landlord account IDs instead of
`count`. Resource addresses then use keys such as
`aws_s3_bucket.landlord_media["la-003"]`, so removing `la-002`
does not shift the identity of `la-003` or `la-004`.

For existing resources, migrate the Terraform state addresses
with appropriate `moved` blocks (or a reviewed state migration)
before applying the change. Changing the resource addressing
scheme without migration can itself produce unnecessary
destroy/create actions.

## Safety

I inspected the plan only. I did not run `terraform apply`
or `terraform destroy`.


## Remediation verified

Replaced `count` with `for_each = toset(var.landlord_accounts)`,
using each landlord account ID as the stable resource key.

Added four `moved` blocks to map the existing indexed state
addresses to the corresponding keyed addresses.

Validation succeeded, with a separate lifecycle-rule warning” to say validation initially had a warning, which was later resolved
The subsequent `terraform plan -refresh=false` recognized all
four address moves and reported:

- 2 to add
- 0 to change
- 0 to destroy

The two additions are the listing media bucket and its lifecycle
configuration. No landlord bucket replacement or destruction
was proposed. No apply or destroy was performed.
